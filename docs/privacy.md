# 隐私模型：内容机密性与元数据

本文档把两件常被混为一谈的事情明确分开：

- **内容机密性（content confidentiality）**：请求/响应中的字节、目标域名、方法、头部、正文是否
  能被观察到。Veilink 用每帧前向保密的 AEAD 保护这些内容。
- **元数据隐私（metadata privacy）**：即使内容不可读，观察者仍能从**谁、何时、多少、多久**中推断
  出什么。Veilink **只部分**处理这一问题，并且必须诚实说明它的边界。

> **不得声称的内容。** Veilink 不做、也不能做以下主张：**零检测率**（"看不出这是 Veilink"
> 或"看不出你在访问什么类别"）、**绝对匿名**、**不可追踪**。任何把本项目的填充、cover traffic 或
> h2 外观描述成上述效果的说法都是错误的。下面逐项说明原因。

代码来源：[`frame.rs`](../crates/veilink-protocol/src/frame.rs)、
[`codec.rs`](../crates/veilink-protocol/src/codec.rs)、
[`session.rs`](../crates/veilink-protocol/src/session.rs)、
[`http2.rs`](../crates/veilink-transport/src/http2.rs)、

[`resolver.rs`](../crates/veilink-server/src/resolver.rs)。

## 1. 内容机密性：保护了什么

| 内容 | 是否对被动网络观察者可见 | 说明 |
|------|------------------------|------|
| 请求/响应正文 | 否 | 在 AEAD 密文内 |
| 目标主机名（域名） | 否 | 在 `OPEN_STREAM` 的加密净荷内；PROXY 路径下客户端不做本地解析 |
| 目标端口 | 否 | 同上 |
| 流 id | 否 | 在加密净荷内 |
| HTTP 方法、URL、头部、Cookie | 否 | 整段在加密净荷内 |
| 帧内是真实流量还是 cover 流量 | 否（密码学上不可区分） | `COVER_DATA` 使用与数据帧完全相同的每帧密钥与 AEAD |
| 会话 id | 是（可见，但是随机的派生值） | 无法关联到任何身份 |
| 帧长度（桶化后） | 是 | 见第 3 节 |
| 方向、帧数、序号、算法 id、key id | 是 | 见第 4 节 |

对**服务端**（VPS）而言：它是被信任的出口。它能看到所有 PROXY 目标的**域名与端口**，因为远端
解析由它执行。它看不到的是 DIRECT 流量的任何信息，也看不到 TLS/HTTPS 的明文（Veilink 不终止
TLS）。

## 2. 填充（padding）：始终生效

填充发生在 **AEAD 明文内部**，因此它是被认证的、在线上不可见的：

```text
明文 = u16 真实长度 | 消息字节 | 随机填充
明文总长被向上取整到"桶"
```

默认桶（`BucketedPadding::new()`）：

```text
512, 1024, 2048, 4096, 8192  字节
超过 8192 后：按 8192 的整数倍向上取整，直到 MAX_PAYLOAD = 65536
```

填充字节来自操作系统 CSPRNG（不是全 0 的规律模式）；只有 RNG 失败时才退化为 0 填充，此时长度
不变，仅削弱该帧的长度隐藏效果。

### 2.1 元数据效果

- 观察者看到的密文长度只反映"桶"，不反映真实消息长度。例如 3 字节与 500 字节的消息都会产生
  512 字节的明文。
- 因此**长度分布被粗化**，而不是被消除。

### 2.2 带宽预算（这是真实成本）

线上帧大小 = `76 (头部) + 桶 + 16 (tag) = 桶 + 92` 字节：

| 真实消息长度 | 明文桶 | 线上帧大小 | 填充浪费 |
|-------------|--------|-----------|---------|
| 1 – 510 | 512 | 604 | 最高 ~99%（极小消息） |
| 511 – 1022 | 1024 | 1116 | ~50% |
| 1023 – 2046 | 2048 | 2140 | ~50% |
| 2047 – 4094 | 4096 | 4188 | ~50% |
| 4095 – 8190 | 8192 | 8284 | ~50% |
| 8191 – 16382 | 16384 | 16476 | ~50% |
| 16383 – 24574 | 24576 | 24668 | ~33% |
| … | 8192 的倍数 | 桶 + 92 | ≤ 100%，最坏接近 2 倍 |
| ≤ 65534 | 65536 | 65628 | 上限 |

要点：

- **每个小控制帧也要占 604 字节**（`KEY_OFFER`、`PING` 等），因为控制帧同样经过填充。
- 最坏情况（消息长度刚好越过桶边界）出现接近 **2 倍**的带宽放大。
- 填充不改变帧数量，只改变每帧大小；它无法隐藏"有多少帧"。

## 3. 流量调度器（traffic scheduler）：**未实现**

`veilink-config` 的模块注释提到 "traffic scheduling" 是协议的一部分并且"始终开启"，但
**代码库中不存在流量调度器**：没有任何定时器、令牌桶、窗口整形或发送节奏控制模块。当前的发送
节奏完全由应用读写驱动：

- 有数据就密封一帧并写出；
- 无数据时什么都不发（除握手后立即发送的一次 `KEY_OFFER` 与需要补货时的 `KEY_OFFER`）。

因此**帧的时序与真实活动的时序高度相关**（见第 4 节）。

## 4. 观察者仍然能看到什么

这是本文档最重要的一节。一个只做被动记录的观察者（ISP、上游运营商、本地网络）能看到：

1. **服务端 IP 与端口**，以及通信的起止时间。
2. **外层是一次 TLS 1.3 握手**；ALPN 为 `h2`（默认传输）或未协商（`tls` 传输，
   此时 ALPN 为 `vlp/1`）。**协议栈嗅探器可以据此判断"这里跑的不是普通 HTTPS 浏览器流量"。**
   `h2` 传输让外层看起来像一个普通的 HTTP/2 会话（`POST`、`content-type: application/octet-stream`、
   路径 `/v1`），但主机名是 `veilink.invalid`、证书是自签名的、SNI 通常是 `veilink.local`
   ——这些特征本身就足以构成指纹。
3. **证书**：服务端使用自签名证书；其 SHA-256 指纹在两次启动之间稳定（除非删除 `state_dir`），
   因此可被用于跨连接关联同一台服务器。
4. **帧层元数据**（全部明文，见 `docs/protocol.md`）：
   - 版本字节 `0x56`、帧类型字节——**这是"正在使用 Veilink"的直接证据**；
   - 每会话随机的 `session_id`；
   - 方向位；
   - 单调递增的 `sequence`；
   - `algorithm` id（1/2/3 随机轮换）；
   - `key_id`（一次性密钥引用）；
   - 密文长度（桶化）。
5. **帧数量与桶化长度**：可以统计"这条连接传了多少帧、每帧属于哪个桶、各方向多少"。
6. **连接时序**：何时建立、持续多久、何时断开；空闲多久后因 `idle_timeout` 被关闭
   （默认 300 秒；客户端与服务端运行时都会把它抬到至少 60 秒）。
7. **请求的节奏**：因为每个应用帧的写出由读写驱动，帧的时间分布与用户活动的时间分布相关。
   一次页面加载的模式（若干小帧、若干大帧、一次停顿）会体现在时序上。
8. **净荷总量**：帧数与桶大小的乘积给出可观测的字节总量（受 TLS 记录层合并/切分影响）。
   TLS 记录层（rustls 的写缓冲）可能把多个小帧合并进一个记录，或把一个大于记录上限的帧切分成
   多个记录；观察者首先看到的是 TLS 记录与 TCP 分段，它们**不一定**与帧边界一一对应。这增加了
   一点不确定性，但**不构成任何保证**：字节总量、方向比例与时间模式依然可见。
9. **DNS 相关元数据**：见第 5 节。
10. **服务端侧的日志**：服务端默认不记录域名（`log.log_domains` 默认 `false`，目标打印为
    `<redacted>`），但它确实解析了域名，且运维者可以打开域名日志。统计计数器
    （`veilink-protocol/src/stats.rs`）**不含域名或 URL**。

### 4.1 由此可以推断什么

- **"这个人在用 Veilink"**：可以（版本字节、ALPN、证书、`veilink.invalid`）。
- **"这些流量去的是你的 VPS"**：可以。
- **流量规模与活跃时间**：可以。
- **是否为同一条会话/同一台服务器**：可以（`session_id`、证书指纹）。
- **具体访问了哪个网站**：不能从密文直接得到；但可以通过**流量关联与网站指纹**间接推断
  （见 `docs/threat-model.md`）。

### 4.2 为什么不能声称"零检测率"

- 帧头、ALPN、自签名证书与 `veilink.invalid` 都是强特征；流量分类器可以据此识别协议。
- 即使隐藏了上述所有特征，**流量模式本身**（包长分布、时序）仍可用于分类；填充只把长度粗化到桶，
  并没有消除分布差异（例如大文件下载与网页浏览的桶分布截然不同）。
- 本项目**没有**做任何抗分类评估、没有对抗性训练、没有真实网络下的检测率测量。
  任何"检测率"数字都不存在于本仓库中。

### 4.3 为什么不能声称"绝对匿名/不可追踪"

- 服务端 IP 是明文可见的；服务端运维者知道你的来源 IP（除非你再叠加 Tor/VPN 等其它手段）。
- 网络观察者可以把"你的入口链路"与"到 VPS 的链路"做**时间与体积关联**。
- Veilink 不隐藏"你使用了这个服务"，也不隐藏你与它的网络位置关系。
- 它不是匿名网络：没有洋葱路由、没有混币式批处理、没有延迟/覆盖网络设计。

## 5. DNS 隐私边界

| 场景 | 谁做解析 | 本地 resolver 是否看到域名 |
|------|---------|--------------------------|
| 白名单命中的域名（PROXY） | **服务端**（`Resolver::resolve_ipv4`，仅 A 记录） | **否**（客户端把规范化域名原样放进加密帧） |
| 白名单命中的 IPv4 字面量 | 无需解析 | 否 |
| 未命中白名单的域名（DIRECT） | 客户端本地系统 resolver | **是** |
| 白名单命中但隧道不可用 | 不解析，直接失败（fail closed） | 否 |
| 客户端自身到服务端的连接（`server` 是域名时） | 客户端本地系统 resolver | 是（看到 VPS 域名） |

因此：

- PROXY 路径确实把**目标域名的解析搬到了 VPS**，本地 resolver 不会看到它。
- **但**以下情况会让域名绕过 Veilink 的代理边界：
  - 浏览器/操作系统的 **DNS 预解析（prefetch / preconnect）** 可能直接向本地 resolver 查询；
  - 浏览器启用 **DoH/DoT** 时，查询由浏览器直接发往 DoH 服务商，完全不经代理；
  - 应用直接使用系统 resolver 而非代理，或流量根本不走 HTTP 代理（见 README 的显著提示与
    `docs/threat-model.md` 的 DNS 泄露一节）；
  - **ESNI/ECH 未启用时**，即使在隧道内，服务端侧看到的是域名（服务端本来就需要它）；
    而在 DIRECT 路径上，TLS SNI 会暴露给网络观察者。

服务端解析行为：仅查询 **A 记录**（`LookupIpStrategy::Ipv4Only`），有界 TTL 缓存（默认 512 条，
TTL 钳制在 5 秒至 1 小时），每查询超时默认 5000 ms、尝试 2 次；**不缓存否定结果**。

## 6. 已实现 / 未实现 一览

| 机制 | 状态 | 说明 |
|------|------|------|
| 固定桶填充 | **已实现且始终生效** | `BucketedPadding`，桶 512–8192 与 8192 的倍数，上限 65536 |
| 随机填充字节 | **已实现** | CSPRNG；RNG 失败时退化为 0 填充 |
| `COVER_DATA` 消息与每帧密码学 | **已实现** | `Message::Cover`、`Session::send_cover`、`cover_*` 计数器 |
| cover 帧的**调度**（自动发送） | **未实现** | 代码库中除测试/基准外无调用者；没有定时器或预算策略 |
| `PaddingPolicy::cover_len`（cover 长度选择） | **已实现但未接线** | 仅测试与基准调用 |
| 流量调度器 / 发送节奏整形 | **未实现** | 无对应模块 |
| keepalive `PING`/`PONG` | **已实现但未定时发送** | `Session::ping()` 仅测试调用；空闲由 `idle_timeout` 关闭 |
| h2 外观（普通 HTTP/2 会话） | **已实现** | 默认传输；但证书、SNI、`veilink.invalid` 仍是特征 |
| 域名日志默认关闭 | **已实现** | `log.log_domains: false`，目标显示为 `<redacted>` |
| 抗流量分类/抗指纹评估 | **未实现** | 仓库中没有任何检测率测量 |

### 6.1 若启用 cover traffic 的预算

由于没有调度器，下面是**设计上的**资源预算，供将来实现时参考；当前不会被实际消耗：

- 每个 cover 帧使用与数据帧相同的每帧密码学（一次 X25519 交换 + 一次 AEAD），因此它的
  **计算成本约等于一帧真实数据**（可用 `benches/benches/privacy.rs` 的
  `cover_traffic_seal/*` 测量）。
- 一个 cover 帧的线上大小同样是"桶 + 92"字节。
- 若以固定速率 r 帧/秒发送，且平均桶为 B 字节，则额外带宽约为 `r × (B + 92)` 字节/秒。

必须同时说明其**局限**：`Session::send_cover` 的文档注释指出"观察者无法从构造上区分 cover 与
真实数据——只能通过 cover 帧不产生响应这一点"。这意味着：如果观察者能看到双向流量，**缺少响应
本身**就是可利用的特征；单纯的单向 cover 并不能消除这一差异。

## 7. 结论：诚实的能力边界

Veilink 提供的隐私属性是：

- **内容机密性**（对被动观察者），具有每帧前向保密；
- **目标域名的本地隐藏**（PROXY 路径下不做本地解析）；
- **长度粗化**（固定桶填充，始终生效）；
- **默认不记录域名**。

Veilink **不提供**：

- 协议存在性的隐藏（观察者可判定"这是 Veilink"）；
- 元数据的隐藏（时序、帧数、字节量、服务端 IP）；
- 抗流量关联或抗网站指纹；
- 抗能读取宿主机内存或实时入侵服务端的攻击者；
- 匿名性（服务端知道你的 IP，网络观察者知道你在用这个服务）。
