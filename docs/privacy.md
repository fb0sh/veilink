# 隐私模型：内容机密性与元数据

本文档把两件常被混为一谈的事情明确分开：

- **内容机密性（content confidentiality）**：请求/响应中的字节、目标域名、方法、头部、正文是否
  能被观察到。Veilink 用每帧前向保密的 AEAD 保护这些内容。
- **元数据隐私（metadata privacy）**：即使内容不可读，观察者仍能从**谁、何时、多少、多久**中推断
  出什么。Veilink 通过 **Strict Privacy 层**（`veilink-privacy` crate）**降低**这一问题的严重性，
  但**不能消除**它。

> **不得声称的内容。** Veilink 不做、也不能做以下主张：**零检测率**（"看不出这是 Veilink"或
> "看不出你在访问什么类别"）、**绝对匿名**、**不可追踪**。填充、批量发送与 cover traffic 是
> **降低信号质量**的措施，不是隐藏。任何把这些机制描述成上述效果的说法都是错误的。

代码来源：[`crates/veilink-privacy/`](../crates/veilink-privacy/)（padding / scheduler / cover /
budget）、[`frame.rs`](../crates/veilink-protocol/src/frame.rs)、
[`codec.rs`](../crates/veilink-protocol/src/codec.rs)、
[`session.rs`](../crates/veilink-protocol/src/session.rs)、
[`http2.rs`](../crates/veilink-transport/src/http2.rs)。

## 1. 内容机密性：保护了什么

| 内容 | 对被动网络观察者可见？ | 说明 |
|------|----------------------|------|
| 请求/响应正文 | 否 | 在 AEAD 密文内 |
| 目标主机名 | 否 | 在 `OPEN_STREAM` 的加密净荷内；PROXY 路径下客户端不做本地解析 |
| 目标端口 | 否 | 同上 |
| 流 id、HTTP 方法、URL、头部、Cookie | 否 | 全部在加密净荷内 |
| 一帧是真实数据还是 cover 数据 | 否（密码学上不可区分） | cover 帧与数据帧使用相同的消息类型与每帧密钥 |
| 会话 id | 是 | 每会话随机的派生值，无法关联到身份 |
| 帧长度（桶化后） | 是 | 见第 2 节 |
| 方向、帧数、序号、算法 id、key id | 是 | 见第 4 节 |

对**服务端**（VPS）而言：它是被信任的出口，能看到所有 PROXY 目标的**域名与端口**，因为远端解析
由它执行。它看不到 DIRECT 流量的任何信息，也看不到 TLS/HTTPS 明文（Veilink 不终止 TLS）。

隐私层（填充/调度/cover）**只在客户端与服务端进程内部工作**，它不接触也不会记录域名、URL 或
任何净荷字节——`SessionCoverSink` 只观察会话的帧计数器。

## 2. 填充（padding）：始终生效，且受预算约束

填充发生在 **AEAD 明文内部**，因此被认证、在线上不可见：

```text
明文 = u16 真实长度 | 消息字节 | 随机填充
明文总长被向上取整到"桶"
```

- 桶定义在协议层（[`codec::BucketedPadding`](../crates/veilink-protocol/src/codec.rs)）：
  `512, 1024, 2048, 4096, 8192`，超过 8192 后按 8192 的整数倍向上取整，上限 `MAX_PAYLOAD = 65536`。
- 运行时安装的策略是
  [`privacy::padding::BudgetedPadding`](../crates/veilink-privacy/src/padding.rs)：它先向桶策略询问
  目标长度，再把**填充开销**提交给预算（`BudgetTracker::request_padding`）。
  - 预算充足 → 使用标准桶。
  - 预算饱和 → **降级到最小桶**（`min(512, MAX_PAYLOAD)` 与 `message_len + 2` 的较大者），
    而**不是关闭填充**。"会静默关闭自己的策略比可预测地降级的策略更糟"。
- 填充字节来自操作系统 CSPRNG；只有 RNG 失败时才退化为 0 填充（长度不变，仅削弱该帧的长度隐藏）。
- 默认填充预算：**每秒 4 MiB**（`Budget::padding_bytes_per_second`，滑动 1 秒窗口，独立于 cover
  预算）。它只在"每帧额外填充字节之和"上计费。
- 计数器：`BudgetedPadding::offered()` / `refused()` 与 `BudgetTracker::padding_total()`。

### 2.1 元数据效果与带宽成本

线上帧大小 = `76 (头部) + 桶 + 16 (tag) = 桶 + 92` 字节：

| 真实消息长度 | 明文桶 | 线上帧大小 | 填充浪费 |
|-------------|--------|-----------|---------|
| 1 – 510 | 512 | 604 | 最高 ~99% |
| 511 – 1022 | 1024 | 1116 | ~50% |
| 1023 – 2046 | 2048 | 2140 | ~50% |
| 2047 – 4094 | 4096 | 4188 | ~50% |
| 4095 – 8190 | 8192 | 8284 | ~50% |
| 8191 – 16382 | 16384 | 16476 | ~50% |
| 16383 – 24574 | 24576 | 24668 | ~33% |
| … | 8192 的倍数 | 桶 + 92 | 最坏接近 2 倍 |
| ≤ 65534 | 65536 | 65628 | 上限 |

要点：**每个小控制帧也占 604 字节**（`KEY_OFFER`、`PING` 等同样经过填充）；最坏情况（消息长度刚好
越过桶边界）出现接近 **2 倍**的带宽放大；填充只改变每帧大小，**不改变帧数量**。

## 3. 流量调度器（scheduler）：批量合并生效，节奏整形当前未生效

### 3.1 设计

发送路径由 [`SendScheduler`](../crates/veilink-protocol/src/scheduler.rs) 抽象，运行时安装
[`PrivacyScheduler::strict()`](../crates/veilink-privacy/src/scheduler.rs)（客户端与服务端都安装）。
默认参数（`SchedulerConfig::default()`，**不可通过 YAML 配置**）：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `max_batch` | 16 | 一次写入最多合并的帧数 |
| `max_batch_bytes` | 64 KiB | 一次写入最多合并的明文字节数 |
| `base_delay` | 200 µs | 批与批之间的基础间隔 |
| `jitter` | ≤ 2 ms | 在基础间隔之上加的随机量（CSPRNG） |
| `max_delay` | 50 ms | 任何延迟的硬上限 |

不变量（由 `veilink-protocol` 的 writer 与策略共同保证）：

1. **没有无界延迟**：策略返回有限值，writer 还用 `SessionConfig::schedule_max_delay`
   （默认 50 ms）再钳一次。
2. **没有饥饿**：已经等待超过 `max_delay` 的消息立即发送。
3. **work-conserving**：队列后面没有待发消息时，等待没有收益，延迟为 0。

### 3.2 当前实际效果（重要）

**批量合并**（`max_batch` / `max_batch_bytes`）**已经生效**：writer 会把队列中已有的消息合并成
一次写入，因此降低了每帧一次 `write` 的系统调用边界，也让若干帧落在同一个 TLS 记录里。

**节奏整形（`delay`）也已生效。** 契约是：`SendScheduler::delay` 在 `queued_behind == 0`
（本批之后没有排队消息）时返回 `Duration::ZERO`，在 `queued_behind > 0` 时返回一个带抖动的
非零值；`writer_task`（见 `veilink-protocol/src/session.rs`）只要拿到非零值就睡眠，并把它硬性
限制在 `schedule_max_delay`（50 ms）以内。也就是**只有"后面还有东西要发"时才等**，等待的目的
是让若干帧落进同一批，而不是给空闲连接凭空制造节奏。

三条边界必须同时说明：

- **等待有上限**：单帧最多被推迟 50 ms，且 `oldest_wait >= max_delay` 时立即发送，因此不会
  饿死任何流；
- **工作守恒**：队列为空时延迟恰好为零，不引入额外延迟；
- **削弱 ≠ 消除**：节奏整形削弱的是"每帧一次写出"的细粒度时间特征，**不等于时序不可分析**。
  帧数、方向比例、桶大小和整体持续时间仍然可见，本仓库也没有任何检测率测量。

## 4. Cover traffic：已实现、默认开启、有硬预算

cover 帧是**真正的 VLP/1 应用帧**（`Message::Cover`，类型 `0x32`），承载随机字节，使用与用户数据
完全相同的每帧一次性密钥交换与填充，因此**逐帧不可区分**；只有"某个突发没有产生响应"这一点可以
被利用。

### 4.1 引擎行为

[`CoverEngine`](../crates/veilink-privacy/src/cover.rs) 不是恒定速率的生成器：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| 启动条件 | 会话空闲 ≥ `cover_idle_after = 750 ms` | 活跃传输期间**不会**发送 cover，不浪费带宽 |
| 每突发帧数 | `burst_frames = 3` | 一次突发最多 3 帧 |
| 突发间隔 | `burst_interval = 1500 ms` | 两次突发之间的等待 |
| 单帧净荷 | `min_payload = 64` … `max_payload = 4096` | 与最大填充桶同量级，混入相同尺寸类别 |
| 突发布上限 | `max_bursts = 40` | 约 60 秒后**自动停止**（空闲会话不会永久产生流量） |
| 停止条件 | 会话关闭 / 预算耗尽 / 达到突发上限 | — |

"空闲"由 [`ActivityClock`](../crates/veilink-privacy/src/cover.rs) 判定；
[`SessionCoverSink`](../crates/veilink-privacy/src/cover.rs) 观察会话的 `frames_sent + frames_received`
计数器来刷新该时钟，因此**隐私层从不接触域名、URL 或净荷字节**——两个层次保持解耦。

客户端在 `run_uplink` 中为每个已建立的会话启动一个 cover 任务，并在会话结束时 abort 它；服务端在
`serve_connection` 中做同样的事。**默认开启，无需也无从配置。**

### 4.2 资源预算（硬上限）

cover 走独立的预算窗口（与填充互不影响）：

| 预算 | 默认值 | 说明 |
|------|--------|------|
| `cover_bytes_per_second` | 4 KiB/s | 滑动 1 秒窗口，超出即拒绝（≈ 345.6 MiB/天，若持续运行） |
| `cover_bytes_total` | 256 MiB | **单个会话的生命周期总额**，这是防止账单失控的最终闸门 |
| `max_queued_messages` | 512 | 出站队列上限（与 `SessionConfig::outbound_queue` 默认值一致） |
| `max_scheduling_delay` | 50 ms | 见第 3 节 |

预算语义（[`BudgetTracker`](../crates/veilink-privacy/src/budget.rs)）：

- 速率窗口可以**部分授予**：请求 1000 字节但本秒只剩 400，则授予 400，而不是整体拒绝。
- 生命周期额度耗尽 → 返回 `CoverTotalExhausted`，引擎停止。
- 突发中一旦预算拒绝就**放弃本次突发**，不进入重试循环。
- 计数器：`CoverStats { bursts, frames, bytes, refused }`；会话侧
  `SessionStats::cover_sent` / `cover_bytes` 会被客户端 reporter 汇总到全局
  `Stats::cover_frames_sent` / `cover_bytes_sent`。

### 4.3 必须承认的局限

- cover 帧**不产生响应**。能看到双向流量的观察者可以据此把"只有出、没有回"的突发与真实请求区分开。
  单向 cover 不能消除这一差异。
- cover 只覆盖**空闲期**，且最多约 60 秒；长时间的静默之后仍然会回到"完全静默"。
- 有一个当前实现的细节需要注意：`SessionCoverSink::is_alive()` 会读取 `snapshot.cover_sent`，但随后
  用 `let _ = cover_frames;` 丢弃它，**并没有像注释所说的那样把 cover 帧排除在活动之外**。
  因此 cover 帧自己也会刷新活动时钟——结果是突发之间更容易被推迟（更保守，而不是更激进）。
  这不影响预算上限，但意味着"空闲 750 ms 后开始"的实际节奏并非严格按设计执行。
- 没有任何抗流量分类评估：本仓库**没有**检测率测量、没有对抗性数据集、没有真实网络评估。

## 5. 观察者仍然能看到什么

一个只做被动记录的观察者（ISP、上游运营商、本地网络）能看到：

1. **服务端 IP 与端口**，以及通信的起止时间。
2. **外层是一次 TLS 1.3 握手**；ALPN 为 `h2`（默认）或 `vlp/1`（`tls` 传输）。协议栈嗅探器可以
   据此判断"这里跑的不是普通浏览器 HTTPS 流量"。`h2` 传输让外层像一个普通 HTTP/2 会话
   （`POST`、`content-type: application/octet-stream`、路径 `/v1`），但主机名是 `veilink.invalid`、
   证书自签名、SNI 通常为 `veilink.local`——这些本身就是指纹。
3. **证书**：自签名；SHA-256 指纹在两次启动之间稳定（除非删除 `state_dir`），可用于跨连接关联。
4. **帧层元数据**（全部明文）：版本字节 `0x56` 与帧类型字节（**"正在使用 Veilink"的直接证据**）、
   每会话随机 `session_id`、方向位、单调递增的 `sequence`、`algorithm` id、`key_id`、密文长度。
5. **帧数量与桶化长度**：可以统计帧数、各方向帧数与桶分布。
6. **连接时序**：建立/持续/断开时间；空闲多久后因 `idle_timeout` 被关闭（默认 300 秒，
   运行时下限 60 秒）。
7. **请求节奏**：由于节奏整形当前未生效（第 3.2 节），帧的时间分布仍然与应用活动相关。批量合并
   会把同一批帧压在一起，**减少**了细粒度的"每帧一次写出"特征，但没有加入额外间隔。
8. **净荷总量**：帧数与桶大小的乘积给出可观测的字节总量（受 TLS 记录层合并/切分影响）。观察者
   首先看到的是 TLS 记录与 TCP 分段，它们**不一定**与帧边界一一对应；这增加一点不确定性，
   但**不构成任何保证**。
9. **cover 突发的双向不对称**：见 4.3。
10. **DNS 相关元数据**：见第 6 节。
11. **服务端日志**：默认不记录域名（`log.log_domains: false`，目标显示为 `domain:<redacted>`），
    但服务端确实解析域名，运维者可开启域名日志。全局统计计数器不含域名或 URL。

### 5.1 由此可以推断什么

- **"这个人在用 Veilink"**：可以。
- **"这些流量去你的 VPS"**：可以。
- **流量规模与活跃时间**：可以（cover 会在空闲期加入少量流量，但不会掩盖活跃期的规模）。
- **是否为同一会话/同一台服务器**：可以。
- **具体访问了哪个网站**：不能从密文直接得到；但可通过流量关联与网站指纹间接推断。

### 5.2 为什么不能声称"零检测率"

- 帧头、ALPN、自签名证书与 `veilink.invalid` 都是强特征。
- 即使隐藏上述所有特征，**流量模式本身**（包长分布、时序、突发结构）仍可用于分类。填充把长度
  粗化到桶，但没有消除分布差异；cover 只在空闲期加入少量等量级流量；节奏整形当前未生效。
- 本仓库**没有**任何检测率评估。任何"检测率"数字都不存在于本仓库中。

### 5.3 为什么不能声称"绝对匿名/不可追踪"

- 服务端 IP 明文可见；服务端运营者知道你的来源 IP。
- 网络观察者可以把"你的入口链路"与"到 VPS 的链路"做时间与体积关联。
- Veilink 不隐藏"你使用了这个服务"，也不隐藏你与它的网络位置关系。
- 它不是匿名网络：没有洋葱路由、没有混批、没有延迟网络设计。

## 6. DNS 隐私边界

| 场景 | 谁做解析 | 本地 resolver 是否看到域名 |
|------|---------|--------------------------|
| 白名单命中的域名（PROXY） | **服务端**（`Resolver::resolve_ipv4`，仅 A 记录） | **否**（客户端把规范化域名原样放进加密帧） |
| 白名单命中的 IPv4 字面量 | 无需解析 | 否 |
| 未命中白名单的域名（DIRECT） | 客户端本地系统 resolver | **是** |
| 白名单命中但隧道不可用 | 不解析，直接失败（fail closed） | 否 |
| 客户端到服务端的连接（`server` 为域名时） | 客户端本地系统 resolver | 是（看到 VPS 域名） |

因此 PROXY 路径确实把目标域名的解析搬到了 VPS；**但**以下情况会让域名绕过 Veilink：

- 浏览器/操作系统的 **DNS 预解析（prefetch / preconnect）**可能直接查询本地 resolver；
- 浏览器启用 **DoH/DoT** 时查询不经代理；
- 应用忽略代理设置，或流量根本不走 HTTP 代理；
- **ESNI/ECH 未启用时**，DIRECT 路径上的 TLS SNI 会暴露给网络观察者（PROXY 路径上的域名对网络
  观察者不可见，但服务端本来就需要知道它）。

服务端解析行为：仅 A 记录（`LookupIpStrategy::Ipv4Only`），有界 TTL 缓存（默认 512 条，TTL 钳制在
5 秒至 1 小时），超时默认 5000 ms、尝试 2 次，**不缓存否定结果**。

## 7. 已实现 / 未实现 一览

| 机制 | 状态 | 说明 |
|------|------|------|
| 固定桶填充 | **已实现，始终生效** | 桶 512–8192 与 8192 的倍数，上限 65536 |
| 填充预算（降级而非关闭） | **已实现** | `BudgetedPadding` + `BudgetTracker`，默认 4 MiB/s |
| 随机填充字节 | **已实现** | CSPRNG；RNG 失败时退化为 0 填充 |
| 发送批量合并 | **已实现，生效** | 最多 16 帧 / 64 KiB 合并为一次写入 |
| 发送节奏整形（批间隔 + 抖动） | **已实现，生效** | 仅在本批之后还有排队消息时等待，单帧上限 50 ms（第 3.2 节） |
| cover traffic 引擎 | **已实现，默认开启** | 空闲 750 ms 后开始，3 帧/突发、1.5 s 间隔、最多 40 突发 |
| cover 预算（速率 + 生命周期） | **已实现** | 4 KiB/s、每会话 256 MiB 上限 |
| keepalive `PING`/`PONG` | **已实现但未定时发送** | `Session::ping()` 仅测试调用；空闲由 `idle_timeout` 关闭 |
| h2 外观（普通 HTTP/2 会话） | **已实现** | 默认传输；证书、SNI、`veilink.invalid` 仍是特征 |
| 域名日志默认关闭 | **已实现** | `log.log_domains: false`，目标显示为 `<redacted>` |
| 隐私层可配置 | **未实现** | 所有隐私参数是内部常量，YAML 中没有任何对应字段 |
| 抗流量分类/抗指纹评估 | **未实现** | 仓库中没有任何检测率测量 |
| 恒定速率 cover / 恒定速率填充 | **未实现** | cover 是"空闲突发后停止"，不是恒速生成器 |

## 8. 结论：诚实的能力边界

Veilink 提供的隐私属性是：

- **内容机密性**（对被动观察者），具备每帧前向保密；
- **目标域名的本地隐藏**（PROXY 路径下不做本地解析）；
- **长度粗化**（固定桶填充，始终生效，受预算约束时降级而不关闭）；
- **发送批量合并**与**空闲期 cover traffic**（有硬性速率与生命周期上限）；
- **默认不记录域名**。

Veilink **不提供**：

- 协议存在性的隐藏（观察者可判定"这是 Veilink"）；
- 元数据隐藏（时序、帧数、字节量、服务端 IP）；
- 经过验证的时序混淆（节奏整形已生效且单帧上限 50 ms，但其抗指纹效果未经任何评估）；
- 抗流量关联或抗网站指纹；
- 抗能读取宿主机内存或实时入侵服务端的攻击者；
- 匿名性（服务端知道你的 IP，网络观察者知道你在用这个服务）。

**不得**把上述任何机制描述为"零检测率""无法识别""绝对匿名"或"不可追踪"。
